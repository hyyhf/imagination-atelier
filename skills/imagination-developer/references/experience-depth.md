# 从展示到值得使用的体验

用一段真实任务检查作品，避免把更多控件当成进步。

## 用户何时会觉得鸡肋

- 默认示例好看，换自己的内容就难操作、出错或没有输出。
- 修改入口藏在长页面里，用户在画面、输入和结果之间反复寻找。
- 参数改变了，但用户看不出改变对任务意味着什么。
- 提供很多独立功能，选择、显示、统计和导出却不属于同一方案。
- 完成后只能截图，用户仍要手工重做主要成果。
- 给任何题材都套相同工具条与版本册，增加步骤却没有帮助判断。

## 以关系设计能力

空间：对象真实尺寸 → 直接摆放与编辑 → 占地／遮挡／装配反馈 → 可使用的尺寸图或方案。镜头操作服务空间判断，不能顶替对象操作。

数据：自己的输入 → 选择变量与方法 → 比较结果和诊断 → 能追溯条件的报告。不要把某个误差最小自动解释成所有场景下最好。

时间与资源：事件／对象 → 时间线或空间上的直接调整 → 冲突与总量 → 能接入后续安排的文件。

创作与叙事：真实内容 → 编辑组织与节奏 → 完整体验 → 分享、保存或导出的成果。纯观看也可以成立，但要有充分内容和独特表达。

以上是能力关系，不是所有任务都必须具备的菜单。

## 默认示例应承担教学

放入有代表性的内容，显示一个可以亲自改变的条件，以及变化的意义。第一个动作不应只是“开始”或打开说明。给用户接入自己内容的明显入口；危险或不可逆操作才增加确认。

让常用操作接近对象与反馈。大型工作台优先用固定视图区、属性区和结果摘要；可以滚动次要详情，不把主要画面和其必要输入隔开。窄屏可以改为聚焦某一步，不压缩成不可读的小画布。

在实际常用屏幕尺寸上检查这些区域是否真的同时出现：源代码在同一容器里并不代表浏览器中在同一屏。画布应按显示区域的比例重新绘制，不能把固定大画布压扁来腾地方。次级工具不应作为永久悬浮层遮住结果或主要操作。

## 现场检验

选一份自己的或新的合理输入，连续做几次修改。观察选中对象是否丢失、关键结果是否同步、错误是否能恢复、主要动作是否容易找到。保存后换一份页面恢复，再打开真实导出结果。

对比改进前后：哪个原本难完成的任务现在可以做？哪个动作减少了？哪个变化更容易理解？哪些表现细节帮助判断？如果只能回答颜色、布局和按钮数量，继续修订主任务。

测试规模按任务风险决定。不要把所有作品都强制塞进庞大的验收流程；保留与实际用途相关的检查。
